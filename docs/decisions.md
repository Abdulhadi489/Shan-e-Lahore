# Decisions

One line each: date, decision, why.

- 2026-10-11: React 19 instead of 18. react-leaflet 5 requires it and React 18 gets no new features.
- 2026-10-11: Self-host fonts (@fontsource) instead of Google Fonts. Faster, no visitor IPs sent to Google, smaller CSP.
- 2026-10-11: CSV export instead of SheetJS. The npm `xlsx` package has unpatched high-severity advisories that fail `npm audit`.
- 2026-10-11: Node 24 LTS, pinned via `.nvmrc` and `engines`.
- 2026-10-11: `.npmrc` sets `min-release-age=14` and `save-exact` so npm itself enforces the dependency rule.
- 2026-10-11: fsevents install script denied (`allowScripts`). It ships a prebuilt binary; the script only rebuilds it.
- 2026-10-11: Local Supabase uses `auto_expose_new_tables = false` to match new cloud projects; every table needs explicit GRANTs.
- 2026-10-11: gitleaks runs as a pre-commit hook via `core.hooksPath=.githooks`, set by `npm install` (`prepare` script).
- 2026-10-12: `docs/specs.md` renamed to `docs/spec.md` to match CLAUDE.md.
- 2026-10-12: Staff may edit items or the address during the confirmation call (Milestone 3, `edit-order` Edge Function re-prices server-side).
- 2026-10-12: Order Staff may pause delivery (`branch_settings.delivery_enabled` only; a trigger blocks other columns).
- 2026-10-12: Guest orders become visible to an account only after staff confirm an order from that account. No SMS means signup does not prove phone ownership. **Superseded 2026-10-12:** no customer accounts at launch; kept as the phase 2 design.
- 2026-10-12: Tracking tokens stored as-is, not hashed. Staff need the link for WhatsApp messages; a hash adds nothing once the database itself is exposed.
- 2026-10-12: Status, payment and call rules live in the `orders` and `call_attempts` triggers only. The three staff Edge Functions are dropped: one copy of the rules cannot drift.
- 2026-10-12: Synthetic signup email is `<phone>@phone.invalid` (reserved TLD, never deliverable, independent of the domain we buy later). Email changes are blocked by a trigger on `auth.users`. **Superseded 2026-10-12:** staff log in with real emails; no phone logins.
- 2026-10-12: One `audit_log` table filled by a trigger replaces `pricing_change_log`; it also covers staff role changes and opening hours.
- 2026-10-12: Every menu row and discount code carries `branch_id`, with composite foreign keys so a child stays in its parent's branch.
- 2026-10-12: Dropped redundant columns: `addon_groups.is_required` (= min_select >= 1), `call_attempts.outcome` (a row is a missed call), `profiles.phone`. Discount usage is counted from orders, not stored.
- 2026-10-12: Added `items.is_featured` for the home page's featured deals and popular items, chosen by the Super Admin.
- 2026-10-12: Default privileges revoked for postgres-created objects, including EXECUTE on new functions from PUBLIC. Anything new needs an explicit GRANT.
- 2026-10-12: Customer and rider phones must be mobiles (`^923\d{9}$`) because they receive WhatsApp messages; branch phones also allow landlines and UAN numbers.
- 2026-10-12: Dev project `shan-e-lahore-dev` (Mumbai) created and linked. Migrations applied; email confirmation off, 8-character passwords, Turnstile CAPTCHA on (secret set in the dashboard only, never in git). Local email-OTP settings matched to the hosted defaults so `config push` changes only what we intend. **Partly superseded 2026-10-12:** passwords are now at least 12 characters and public signup is off.
- 2026-10-12: **No customer accounts at launch; guest checkout only** (approved by the client). Customers never sign up or log in; they follow orders through the tracking link. No "remember me on this device": nothing about the customer is stored on their phone except the language choice. Why: without free one-time codes (no SMS) customer login would mean phone + password with resets done by the owner over the phone (workload and social-engineering risk); anyone could squat someone else's number; a public signup endpoint is an attack surface; it saves about 4-5 days of the 4-week plan; customers here are used to guest checkout (for example Goga Naqibia's Shopify checkout). Customer accounts move to phase 2 if customers ask.
- 2026-10-12: **Staff and Super Admin log in with real email + password only; no MFA (no authenticator app).** Why: keep the project simple for an unpaid student team. **Risk accepted by the team:** these accounts can read customers' names, phones and home addresses, and the login page is public, so a leaked or guessed password exposes that data. Mitigations: minimum 12-character passwords, Turnstile on login, Supabase's built-in login rate limits, individual accounts (never shared), leavers deactivated. Supabase MFA is free and can be switched on later in about half a day.
- 2026-10-12: Public signup off (`[auth] enable_signup = false`). `[auth.email] enable_signup` stays `true` because it switches email login itself (supabase/cli#7055: turning it off locks everyone out). Accounts are created only by `super_admin`.
- 2026-10-12: No email sending at launch (Supabase's built-in email only reaches organisation members; custom SMTP would be a new service needing the real domain). `super_admin` resets staff passwords through `admin-users`; there are always at least two `super_admin` accounts; README has a last-resort dashboard recovery.
- 2026-10-12: `admin-users` scope is exactly: create staff, deactivate staff, reset staff password.
- 2026-10-12: The trigger blocking email changes on `auth.users` stays. It also blocks the admin API, so changing a staff email means creating a new account and deactivating the old one. Keeps the audit trail tied to one identity per account.
- 2026-10-12: Removed the customer-account pieces from the database (the `addresses` table, `customers.user_id`, `phone_verified_at`, `preferred_language`, `orders.user_id`, `private.current_customer_id()`, customers-read-own policies, phone verification on confirm). No dead code and a smaller attack surface; phase 2 can restore them from git history. The `customers` table stays: one row per guest phone, for blocking and reports.
- 2026-10-12: New users get the no-access role `customer` from the trigger; their display name falls back to the part of the email before "@" so Dashboard > Add user works without metadata.
- 2026-10-12: Design tokens measured from the logo (orange `#F39100`, black `#22211E`) and the printed menu (peach-to-orange gradient). Tailwind's default colours and radii are removed so only our tokens exist. White text on the logo orange fails contrast (2.4:1), so orange buttons carry ink text and orange text uses `brand-deep`. Swap the values in `src/index.css` when the client sends official brand colours.
- 2026-10-12: Headings use PT Sans Narrow Bold (OFL), a free stand-in for the menu's Myriad Pro Condensed (Adobe licence, can't be self-hosted). Body text uses the phone's own font (0 KB). The menu prints Urdu in Naskh; we keep Noto Nastaliq Urdu as the spec says, regular weight only (each weight is 156 KB) with `font-synthesis: none` so no fake bold.
- 2026-10-12: The admin panel is English only (team decision). Its text still lives in `en.json`, so Urdu can be added later; `/admin` forces `lang="en" dir="ltr"` whatever the customer site was last set to.
- 2026-10-12: React Router in declarative mode (`BrowserRouter` + `Routes`): TanStack Query does the data loading, so data-router loaders would be a second way to do the same thing. `/admin` is a lazy chunk so customers never download staff code.
- 2026-10-12: Turnstile is loaded by a small component (`src/components/Turnstile.tsx`) instead of a wrapper package. Local development uses Cloudflare's always-pass test site key `1x00000000000000000000AA`. **`localhost` is allowed on the real widget for testing against the hosted dev project; remove it before launch** (Cloudflare advises against local hostnames on production keys).
- 2026-10-12: The login page never says whether the email or the password was wrong, so it can't be used to discover staff emails.
- 2026-10-12: Phone normalisation also accepts Urdu-keyboard digits and `+92 0300…`, which are unambiguous. Landlines are rejected, matching the database CHECK.
- 2026-10-12: `npm audit` reports a high advisory in `source-map-js` 1.2.1 (build-time only, via Vite and Tailwind; never shipped to browsers). The fix, 1.2.2, was published 2026-09-30, inside our 14-day window; update it on or after 2026-10-14, before CI runs `npm audit`.
- 2026-10-12: CI actions are pinned to commit SHAs (Dependabot updates them). Actions and tools follow the 14-day rule too: setup-node v7.0.0 rather than v7.1.0, and Supabase CLI 2.118.0 in CI while local machines run 2.120.0. CI and Render install with `npm ci --ignore-scripts`, so no package install scripts run on build machines.
- 2026-10-12: The Database workflow runs only when `supabase/` changes: a run takes about 5 minutes and the private repo's Actions minutes (2,000 a month) come from the owner's free account. It starts only the database, Auth and Storage, and fails on any `db lint` or Security Advisor warning.
- 2026-10-12: gitleaks in CI is the official release binary checked against its published SHA-256, not gitleaks-action, which needs a licence once the repo belongs to an organisation.
- 2026-10-12: Render deploys a commit only after its checks pass (`autoDeployTrigger: checksPass`), so pushing to main is deploying and the ask-before-push rule covers deploys. Arslan owns the Render account; Hadi, who owns the repo, approves Render's GitHub app.
- 2026-10-12: The public `VITE_` values live in `render.yaml`, next to the Content-Security-Policy that must name the same Supabase URL, so they change together. The CSP is an allowlist (our files, our Supabase project, Turnstile). Cloudflare recommends a nonce-based CSP, but nonces need a server per request and a static site has none.
- 2026-10-13: The dev seed is the real printed menu (2026-08-29): names, prices and the restaurant's own Urdu. Rice prints a "Qtr" column with no prices, so rice has Half/Full only. Deals list single pieces, not menu portions, so their contents are a description, not `deal_items`. The printed menu has no add-ons, so the seed has none; add-on rules are covered by the shared pricing tests.
- 2026-10-13: Menu oddities at launch need no code: "Kari Pakora (Tue/Wed)" is marked sold out by staff on other days; fish sold by weight is offered as fixed sizes (½ kg / 1 kg, Boneless 1 kg) and staff adjust on the call.
- 2026-10-13: The cart survives a refresh: localStorage keeps the dish choices and quantities only (team decision; CLAUDE.md section 5 updated). Never name, phone or address.
- 2026-10-13: Until the client sends real values, development uses placeholders: minimum order Rs 800, tiers 3/5/7 km at Rs 100/150/200, hours 12:00-02:00 daily.
- 2026-10-13: Three Supabase environments: **local** (Docker, seed data), **dev** (hosted `shan-e-lahore-dev`, test data only, what the Render site uses for now) and **production** (created before launch in Milestone 4, real orders, Supabase Pro recommended). Schema changes go local, then dev, then production; production data never leaves production. The Render site switches to production by changing the `VITE_` values and the CSP in `render.yaml` together.
- 2026-10-13: Security Advisor on the hosted dev project shows two warnings, both accepted for dev: leaked password protection is off because Supabase offers it only on Pro and above (switch it on in production), and "insufficient MFA options" is the recorded no-MFA decision.
- 2026-10-13: **Exception to the 14-day rule (team decision):** `source-map-js` 1.2.2 installed at 13 days old to fix a high-severity advisory and get CI green, so the site could deploy the same day. Build-time tool only; the change is one package in the lockfile.
- 2026-10-13: Design skill "taste-skill" (github.com/Leonxlnx/taste-skill, MIT) copied into `.claude/skills/design-taste-frontend/` after review, instead of `npx skills` (installer version under 14 days old). CLAUDE.md wins where they disagree: no Motion library (CSS only), no stock or placeholder photos (real dish photos only), Lucide stays, light theme only for now. The brand's cream and orange are measured from the real logo and menu, which the skill's own override allows.
- 2026-10-13: Branch pin set to 31.523689, 74.344498 (Google Maps listing "Shan-e-Lahore", Gulberg II), sent by the team. Distances and delivery charges are measured from here.
- 2026-10-13: Launch moved forward to Friday 23 October 2026 (team decision). `docs/status.md` holds the day-by-day plan, what is needed from the restaurant by when, and open risks; it is updated with every push.
- 2026-10-13: Order creation is one SQL function, `public.create_order()`, executable only by service_role: customer upsert (blocked numbers refused), the branch's next order number under a row lock, order, lines and add-ons in one transaction. Pricing stays in TypeScript (`_shared/order.ts`) so the website and server share it; the table CHECKs still reject totals that don't add up.
- 2026-10-13: The four customer Edge Functions use `verify_jwt = false` because customers are anonymous; they validate with strict zod schemas, rate-limit through `public.hit_rate_limit()` (hashed keys, no raw IPs or phones stored) and allow only `ALLOWED_ORIGINS`. Shared files import bare `zod`, resolved by each function's `deno.json` on the server and by `node_modules` in the website.
- 2026-10-13: Edge Functions use an untyped Supabase client with explicit row types, not the website's generated types, so deploys don't depend on files outside `supabase/functions`.
- 2026-10-13: The tracking page checks for updates every 30 seconds until delivered or cancelled. It shows payment account details only while unpaid and the rider's name and phone only while out for delivery. Never the address.
- 2026-10-13: The map library (Leaflet, about 46 KB compressed) loads only on checkout and when someone taps "Show the delivery area on a map" on the home page. Map markers are drawn in CSS, so no image files and nothing extra for the CSP; OpenStreetMap tiles are allowed in `img-src`.
